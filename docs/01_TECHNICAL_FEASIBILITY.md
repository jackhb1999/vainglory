## 1. 结论摘要

**在 L2 边界内，GX-01 无不可克服的技术障碍。** 现有仓库已具备正确的架构方向：服务端权威、60Hz 固定步长、UDP/netcode、快照广播、客户端预测与回滚、数据驱动技能、一次完整战斗闭环。技术上真正需要解决的是**从"原型"到"产品"的四个结构性缺口**，而非玩法规则本身：

| 缺口 | 现状 | 影响 | 验证项 |
|---|---|---|---|
| **S1 视野与信息安全** | 快照全量下发、无 AOI/裁剪 | 客户端持有全图信息 → 全图外挂不可避免；这是**架构级**缺陷，不是补丁问题 | TF-03 |
| **S2 网络效率** | 快照/事件全量 `ReliableOrdered`，无 delta | 队头阻塞 + 带宽浪费 2~4 倍；高延迟下手感劣化 | TF-02 |
| **S3 玩法闭环缺失** | 兵线/野怪生成 TODO、商店占位、无胜负判定 | 一局无法自然开始与结束 | TF-05 |
| **S4 生产层为零** | 无账号/数据库/配置化/真重连/反作弊/多平台 | 无法运营、无法合规、无法测量 | TF-06/TF-07 |

**最关键的判断**：上游报告 §2.1 已证实原作因服务器成本停运（Rogue Games 2020-03-27 关服，公开致歉称"服务器成本是天文数字"）。因此 GX-01 的首要技术目标**不是画质，而是单位经济**——必须用可测量的指标（单核并发房间数、单局出口带宽、单局 CPU 毫秒）证明成本模型成立。这一点贯穿本文 §4、§5、§8。

## 2. 技术范围与边界

### 2.1 借鉴范围（规则层，允许）

| # | 规则 | GX-01 内部表述 | 工程标识 |
|---|---|---|---|
| L2-R1 | 3v3、单条主道 + 侧翼野区 | 3v3 / 主道 + 林隙 | `3V3_SINGLE_LANE` |
| L2-R2 | 占领型中立目标（击杀守卫→归属→全队收益/推线） | 辉矿、征募井、渊卫 | `CAPTURE_OBJECTIVE` |
| L2-R3 | 双出装体系（物理向 / 法术向） | 刃能 / 秘能 | `BLADE` / `ARCANE` |
| L2-R4 | 点触操作（并提供摇杆备选） | 点触 + 摇杆双模 | `TAP_CONTROL` |
| L2-R5 | 约 20 分钟对局节奏 | 目标时长 18±4 分钟 | `MATCH_PACE` |

### 2.2 表达层约束（强制，不可协商）

**禁止**：原作名称与商标、原角色名/形象/技能演出、原地图名称与景观设计、原 UI/图标/音乐/音效/台词/世界观、原作数值表与遥测字典、任何"官方/授权/精神续作"表述。

**必须**：原创命名体系、原创美术与音频、自研数值表、独立创作证据链（设计稿 + 提交历史 + 资产来源登记）、CI 禁词检查。术语对照与禁用词表见 `GX-ARCH-2026-001` §2。

> **工程含义**：这条约束会实际影响技术设计——配置表、资源命名、日志字段、协议枚举、动画事件名、甚至测试夹具数据都不得出现禁用词；因此需要一个**自动化门禁**（ADR-10），而非仅靠人工评审。

### 2.3 一期技术范围（Scope In）
单平台优先（桌面端用于验证 → 目标移动端）、1 张地图、3 位英雄（切片）/ 12 位英雄（上线）、3v3 单模式、权威服务器、账号与合规、匹配、运营后台、回放。

### 2.4 一期不做（Scope Out）
5v5 三路、真实视线迷雾（仅做草丛/遮蔽的简化版）、全球多区域同服、Web(wasm) 客户端、自建电竞赛事、皮肤量产、跨平台输入公平性（键鼠 vs 触屏）、主机平台。**每项后移都有成本理由，见 §6 ADR 索引。**

## 4. 关键量化预算

> 全部为**设计预算/待验证阈值**，不是实测值。实测由 §5 的 POC 产出后回填。

### 4.1 时间与帧预算

| 指标 | 预算 | 说明 |
|---|---|---|
| 服务端模拟 tick | 60 Hz（16.67 ms） | 与现状 `Time::<Fixed>::from_hz(60.0)` 一致 |
| 单 tick 逻辑耗时（P95） | **≤ 4 ms** | 留 ≥12 ms 给网络/编码/系统抖动；超过则触发优化 |
| 快照下行频率 | 20~30 Hz（默认 20） | 与 60Hz 模拟解耦，可配置 |
| 客户端输入上行 | 每 tick 或 30 Hz（含冗余重发） | 带序号与时间戳 |
| 客户端渲染帧 | 60 fps（移动端基线），30 fps 为最低可接受 | NFR-02 |
| 输入到画面响应（本地预测） | ≤ 50 ms（P95） | 注意：不是原作宣传的 sub-30ms，那需要引擎级优化，一期不承诺 |
| 预测回滚硬修正率 | ≤ 1 次 / 分钟 / 客户端 | 超过说明预测模型与服务端不一致 |
| 对局目标时长 | 18±4 分钟（P50），硬上限 25 分钟 | L2-R5；超时进入强制结算 |

### 4.2 带宽预算（推导见附录 A）

| 场景 | 预算 |
|---|---|
| 单实体 delta 字段 | 24~32 B（量化 + 位掩码） |
| 单客户端下行 | ≤ 100 kB/s（≈0.8 Mbps） |
| 单客户端上行 | ≤ 8 kB/s |
| 6 人房间服务端出口 | ≤ 0.6 MB/s（≈4.8 Mbps，含协议头 1.5~3× 后上限 ≈15 Mbps） |
| 当前实现的等效值 | 约为预算的 **2~4 倍**（全量 + 可靠有序） |

### 4.3 容量与单位经济（决定项目生死）

单局服务器成本模型：

```
cost_per_match = (match_minutes × 60 × cpu_ms_per_tick / 1000 / 3600 / cores)
                 × cpu_hour_price
               + egress_GB_per_match × bandwidth_price
               + amortized_memory / rooms_per_host
```

| 指标 | 目标阈值 | 备注 |
|---|---|---|
| 单核并发房间数（3v3、60Hz） | ≥ 8 | 由 TF-01 实测；低于 4 则单位经济大概率不成立 |
| 单房间内存 | ≤ 128 MB | 含 ECS 世界、快照历史、回放缓冲 |
| 单局服务端出口流量 | ≤ 0.8 GB | 100 kB/s × 6 人 × 1080 s ≈ 648 MB；玩家侧单局 ≤120 MB，见附录 A.3 |
| 冷启动到可进房 | ≤ 3 s | 影响弹性扩容体验 |
| 崩溃率（客户端会话） | ≤ 0.3% | NFR-06 |

> **判定原则**：垂直切片必须产出 `cost_per_match` 的实测值，并与目标 ARPPU × 付费率 × 对局数比较。若无法覆盖，应收缩范围（更少实体、更低快照频率、更少区域），而不是追加内容。

### 4.4 客户端资源预算

| 项 | 预算 |
|---|---|
| 首包体积（Android） | ≤ 400 MB（不含后续资源包） |
| 运行时内存峰值 | ≤ 700 MB（中端机） |
| 冷启动到可操作 | ≤ 8 s |
| 单局流量（玩家侧） | ≤ 100 MB |
| 设备发热降频 | 连续 2 局不掉出最低帧率档 |

## 5. POC 验证计划（TF）

| ID | 名称 | 方法 | 通过阈值 | 工期 | 失败备选 |
|---|---|---|---|---|---|
| TF-01 | **权威模拟容量基准** | headless 压测：模拟 N 个房间 × 6 客户端，采集 tick P95、内存、CPU | 单核 ≥8 房间、tick P95 ≤4 ms | 3 周 | 降快照频率 / 房间进程化 / 精简实体 |
| TF-02 | **协议分级与 delta** | 用 `InputCmd`/`WorldSnapshot` 加基线+delta，对比全量可靠通道，在 150ms/3% 丢包下测抖动 | 带宽降 ≥50%、无队头阻塞、状态收敛正确 | 3 周 | 换 QUIC / 简化为不可靠 + 周期基线 |
| TF-03 | **服务端视野裁剪** | 实现可见性判定 + 抓包验证 | 客户端**收不到**任何视野外敌方实体字段；裁剪耗时 ≤0.8 ms/tick | 4 周 | 空间哈希分区 / 降实体数 |
| TF-04 | **预测/插值体验** | 挂载 `InterpolationPlugin`，用网络损伤仪测试 5 组 RTT/丢包 | 无可感拉扯；硬修正 ≤1 次/分 | 3 周 | 扩大抖动缓冲 / 降低快照频率 |
| TF-05 | **一局闭环可玩切片** | 补全兵线/野怪/占领目标/塔/胜负，3 英雄，跑 20 局自动对局 | 100% 对局能自然结束并产出正确结算 | 6 周 | 缩小目标数量，保留核心状态机 |
| TF-06 | **平台服务解耦** | 账号/实名/支付最小链路 + 战斗服通过令牌接入 | 战斗服不持有任何 PII；接口契约稳定 | 4 周 | 合并部署但保持 trait 边界 |
| TF-07 | **配置热更与校验** | `ConfigSet` 版本化 + 启动校验 + 运行中切换 | 数值变更无需重启；非法配置被 CI 拒绝 | 3 周 | 灰度重启 |
| TF-08 | **回放与反作弊可行性** | 记录输入+快照，复现任意一局；注入变速/改包/全图挂样本 | 回放逐 tick 一致；基础攻击被阻断 | 4 周 | 仅保留服务端日志审计 |
| TF-09 | **目标机型渲染基准** | 3 档机型 × 程序化地图 + 1 个带骨骼动画英雄 | 中端机 60fps、低端机 ≥30fps | 4 周 | 动态分辨率/LOD；或启动 ADR-01 备选（商业引擎客户端） |
| TF-10 | **版本兼容与灰度** | 协议/配置双版本号，新旧客户端混合压测 | 旧客户端可读新基线或得到明确拒绝，不崩溃 | 2 周 | 强制同版本 |
| TF-11 | **表达层合规门禁** | CI 禁词扫描 + 资产来源登记表校验 | 0 命中；每个资产有来源与作者 | 1 周 | 人工评审清单 |

**排布**：TF-02/03/04 可并行但共享协议改动，建议同一小组串行推进；**TF-01 经澄清 Q-03 移入 M2（G2），与 TF-05 及 `cost_per_match` 实测同期**；TF-09 属 M3/G3 范围；TF-11 应在 M0 最先完成（它是所有提交的前置门禁）。

## 6. 架构决策索引（详见 `GX-ARCH-2026-001` §13）

| ADR | 决策 | 对可行性的影响 |
|---|---|---|
| ADR-01 | 保留 Rust + Bevy 0.20 全栈，演进式重构，不重写 | 复用 6.5k 行骨架；风险是 Bevy 移动端生态（TF-09 兜底） |
| ADR-02 | **服务端权威 + 状态快照**，不采用 lockstep/全量定点 | 规避 f32 跨平台一致性难题；反作弊靠裁剪+校验（TF-03/08） |
| ADR-03 | 模拟核心与渲染解耦，分阶段剥离 `bevy_render` 依赖 | 使同一套逻辑可用于服务端、回放、平衡模拟器 |
| ADR-04 | 网络层抽象 `Transport` trait，renet2_netcode 为默认实现 | 移动端可换实现，Web 端可换 WebTransport，避免平台锁死 |
| ADR-05 | **服务端视野裁剪前置**，先于任何内容开发 | 否则后加会推翻全部协议与客户端假设 |
| ADR-06 | 配置即数据，`ConfigSet` 版本化 + CI 校验 + 热更 | 消除现状全硬编码；支撑平衡迭代与灰度 |
| ADR-07 | 一进程多房间 + 房间隔离与限流 | 单位经济优先；若 TF-01 不达标再改为房间进程化 |
| ADR-08 | 回放与反作弊共用输入/快照日志 | 一份基础设施两用，降低成本 |
| ADR-09 | 产品 UI 与调试 UI 分离，egui 仅作工具层 | 现状 egui 面板不能承担商业 UI |
| ADR-10 | 表达层原创为 CI 强制门禁 | 把法律约束变成可执行检查 |
| ADR-11 | 账号/合规/支付独立服务，与战斗服分离 | 合规变更不触及战斗热路径 |
| ADR-12 | 匹配与编排解耦，battle-server 动态分配 | 修复现状"服务器地址写死"的架构缺陷 |

## 7. 技术风险登记（与上游 §11 对齐）

| ID | 风险 | 概率 | 影响 | 技术缓解 | 关联 TF |
|---|---|---|---|---|---|

| TR-05 | 单核房间数不足 → 单位经济不成立 | 高 | **致命** | 降实体/降快照频率/房间进程化；必要时收缩玩法 | TF-01 |

| TR-07 | 浮点差异在客户端预测中放大 | 中 | 中 | 服务端权威 + 容差修正；仅回放关键字段定点化 | TF-08 |
| TR-08 | 第三方/遗留资产混入发布包 | 中 | 高（法律） | TF-11 门禁 + 资产登记 + 发布前清单 | TF-11 |
| TR-09 | `renet2_netcode` 依赖原生 UDP，移动端/后台受限 | 中高 | 中 | `Transport` 抽象 + 平台实现；生命周期处理 | TF-02 |
| TR-10 | 死代码/未挂载插件造成"看起来实现了"的错觉 | 确定 | 中 | M1 清理清单（见架构 DN-02/DN-03） | TF-04 |

## 8. 技术闸门（Go / No-Go）

| 闸门 | 时点 | 量化判据 | 未通过处理 |
|---|---|---|---|
| **G0 合规技术前置** | M0 | TF-11 通过（禁词 0 命中、资产登记 100%）；法律意见书面确认；仓库命名清理完成 | 禁止任何对外发布与宣传 |

| **G4 单位经济** | M4 | LTV > 获客成本；单局服务器成本在模型内 | 停止扩量，重新设计经济/技术参数 |

> **最重要的闸门是 G2**：原作正是死在单位经济上。G2 若拿不出实测的 `cost_per_match`，后续所有内容投入都是风险敞口。

## 9. 结论

1. **规则层（L2-R1~R5）在现有 Rust/Bevy 技术栈上完全可实现**，且当前仓库的网络骨架方向正确，无需更换技术路线。
2. **四个结构性缺口（视野安全、网络效率、玩法闭环、生产层）都是明确的工程任务**，有清晰的验证方法与量化阈值，不存在未知的科学问题。
3. **最大风险不是技术，是单位经济与法律合规**：前者由 G2 的实测数据裁决，后者由 G0 的门禁与法律意见裁决。
4. 建议按 `M0 合规清理 → M1 架构加固（TF-02~04）→ M2 垂直切片（TF-01 + TF-05 + 成本实测）` 推进；**在 G2 通过前不启动英雄量产与多平台适配，内容量产须待 G4 单位经济验证**（与上游 `VG-FS-2026-001` §12.2 一致）。
5. 本文所有预算与阈值由 POC 实测回填后升版至 v1.1；任何阈值变更须同步更新 `GX-PRD-2026-001` 的 NFR 与 `GX-DEV-2026-001` 的验收用例。

## 附录 A：带宽与容量推导

**A.1 单局实体规模估算（3v3 单线）**

| 类别 | 数量级 |
|---|---|
| 英雄 | 6 |
| 战偶（小兵，双方各 1~2 波在场） | 8~24 |
| 哨塔（含已摧毁状态需同步） | 10~12 |
| 林隙中立单位（营地 + 占领目标守卫） | 12~20 |
| 投射物 / 区域效果 | 0~20 |
| **动态实体合计** | **约 40~80** |

**A.2 字段与编码**

| 字段 | 字节（量化前） |
|---|---|
| net_id | 4 |
| entity_type + flags | 2 |
| position (x,z 各 2B 量化) | 4 |
| facing (1B) | 1 |
| health / energy (各 2B) | 4 |
| level / gold | 3 |
| cooldowns (4 × 1B) | 4 |
| 状态效果位 | 2 |
| changed 位掩码 | 2~4 |
| **合计** | **≈ 26~30 B**（对齐后 32 B） |

**A.3 下行**

```
per_client_Bps = snapshot_hz × visible_entities × bytes_per_delta
               = 20 × 60 × 32 = 38,400 B/s ≈ 37.5 kB/s
```
叠加事件、基线快照（每 2 s 一次全量）、协议头与加密开销（×1.5~3）后，设计预算取 **≤100 kB/s/客户端**。按 3v3 共 6 人（澄清 Q-05），服务端单房间出口约 `6 × 100 kB/s = 0.6 MB/s ≈ 4.8 Mbps`，含开销上限 ≈ 15 Mbps；单局（1080 s）出口约 648 MB。

**A.4 现状对比**

现状把 `WorldSnapshot`（全量、含所有实体）与 `GameEvent` 全部走 `ReliableOrdered` 广播：既无视野裁剪也无 delta，等效字段量约为上式的 2~4 倍，且可靠有序通道对实时状态产生队头阻塞。**改造收益主要不在带宽，而在延迟确定性与信息安全。**

**A.5 容量**

若单 tick 逻辑预算 4 ms、周期 16.67 ms，则理论单核可承载 `16.67 / 4 ≈ 4` 个满负载房间（保守），通过分帧批处理与错峰快照可提升至 8+。**该数值必须由 TF-01 实测，不得直接采用**。
